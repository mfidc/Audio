## 1. Memory taxonomies: what credible sources use and what they store where

### Takeaway
Two taxonomies dominate: the cognitive-science split (working / semantic / episodic / procedural, from CoALA and adopted by LangChain) and the engineering split (in-context vs out-of-context, as in Anthropic and Letta). In practice they converge on the same rule: keep a small always-loaded core (identity, rules, an index), put everything else outside the window, and fetch it on demand.

### Cited Findings
- [S] LangChain's docs adopt the CoALA mapping: semantic memory = facts (used for personalisation), episodic = past experiences (in practice few-shot examples of past agent actions), procedural = "a combination of model weights, agent code, and agent's prompt" that sets behaviour. — [LangChain memory concepts](https://docs.langchain.com/oss/python/concepts/memory); [Harrison Chase, "Memory for agents"](https://blog.langchain.com/memory-for-agents)
- [S] LangChain distinguishes two write paths. "Hot path": the agent decides what to remember during the response, via a tool call; this adds latency and mixes memory logic into agent logic. "Background": a separate process updates memory during or after the conversation; no latency cost, but updates are delayed and you need logic for when to run. — [LangChain long-term memory docs](https://docs.langchain.com/oss/python/langgraph/memory)
- [S] The largest recent survey, "Memory in the Age of AI Agents" (Hu, Liu, Zhang and ~45 co-authors, arXiv 2512.13564, posted 15 Dec 2025, revised 13 Jan 2026), replaces the short/long-term split with three lenses: forms (token-level, parametric, latent), functions (factual, experiential, working), and dynamics (formation, evolution, retrieval). — [arXiv 2512.13564](https://arxiv.org/abs/2512.13564v2)
- [S] A later survey (arXiv 2602.06052) calls 2512.13564 a partial view focused on agent-centric tasks rather than on how memory should be designed and deployed for users. — [arXiv 2602.06052](https://arxiv.org/html/2602.06052v3)
- [S] Another 2025 survey frames memory by representations and operations: "Rethinking Memory in LLM based Agents: Representations, Operations, and Emerging Topics" (arXiv 2505.00675). — [arXiv 2505.00675](https://arxiv.org/pdf/2505.00675)
- [V] Anthropic's framing is in-context vs external. Context is a finite attention budget subject to "context rot"; the goal is "the smallest possible set of high-signal tokens". Three long-horizon techniques: compaction, structured note-taking (agentic memory), and sub-agents that return condensed summaries (often 1,000-2,000 tokens). — [Anthropic, "Effective context engineering for AI agents", 29 Sep 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [V] Claude Code operationalises a two-author split: CLAUDE.md = instructions the human writes (rules, workflows, architecture); auto memory = notes Claude writes (preferences, corrections, project context that cannot be derived from code). Both are "context", not enforced configuration. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Claude Code docs place procedural knowledge in skills: "a procedure or a piece of team knowledge saved at `.claude/skills/<name>/SKILL.md`", lighter on context than CLAUDE.md because only name and description are always loaded. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [S] Letta's original design split memory into in-context "memory blocks" (editable core memory) and out-of-context archival/recall storage; in 2026 it moved to git-backed files (MemFS / "context repositories"). — [Letta, "Memory blocks"](https://letta.com/blog/memory-blocks); [Letta, "Context repositories"](https://www.letta.com/blog/context-repositories)
- [B] Origin of the cognitive taxonomy: Sumers, Yao, Narasimhan, Griffiths, "Cognitive Architectures for Language Agents" (CoALA), arXiv 2309.02427 (2023). Origin of the OS-style in-context/out-of-context split: Packer et al., "MemGPT", arXiv 2310.08560 (2023). Both predate 2025 and are foundational rather than current. — [CoALA](https://arxiv.org/abs/2309.02427); [MemGPT](https://arxiv.org/abs/2310.08560)

Where sources say to store things (synthesised from the items above, each row traceable to the cited source):

| Memory type | Recommended home | Source |
|---|---|---|
| Working memory | Context window, plus a todo / notes file re-read during the task | Anthropic context engineering [V]; Manus [S] |
| Procedural (how to do things) | Rules file (CLAUDE.md / AGENTS.md) for always-on rules; skills for task-specific procedures; hooks for must-always rules | Claude Code docs [V] |
| Semantic (facts, preferences) | Small topic files behind a one-line-per-entry index; or a vector / graph store at scale | Claude Code auto memory [V]; Mem0, Zep [S/V] |
| Episodic (what happened) | Session transcripts kept raw and searched on demand; progress logs; git history | Anthropic long-running harness post [V]; Letta benchmark post [S] |

### Inferences
- The taxonomy matters less than two design decisions: who writes (human, agent in the hot path, or a background process) and what is always loaded versus fetched.
- "Procedural memory = prompt + code" (LangChain) and "skills" (Anthropic) are the same idea at different granularity; skills add progressive disclosure.

## 2. File-based memory: conventions, limits, update rules, and how to stop rot

### Takeaway
The best-documented current practice is a short human-owned rules file (target under 200 lines), an agent-owned memory directory with a one-line-per-entry index capped at 200 lines / 25 KB, on-demand topic files, and skills for procedures. Rot is controlled by hard size caps, dated entries, periodic audits, and moving anything that must always happen out of memory and into hooks.

### Cited Findings

CLAUDE.md / AGENTS.md
- [V] "Target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports (`@path`) organise but do not reduce cost, because imported files load with the importer; maximum import depth is four hops. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] CLAUDE.md is loaded whole (up to 4 MiB; larger files are skipped entirely); a startup warning appears when a file exceeds the recommended length or when files together exceed a combined limit. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] What belongs in it: only "what Claude couldn't work out from the code itself": exact test/typecheck/lint commands, places where the code is misleading, decisions not in the repo, and "anything you've had to correct twice already". `/init` generates a draft and "from there the work is mostly removing lines". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [V] `/doctor` trims content derivable from the codebase ("directory layouts, dependency lists, and architecture overviews") and keeps "pitfalls, rationale, and conventions that differ from tool defaults". `/doctor prompt-audit` flags instructions written for older models, references to files or commands that no longer exist, and files that contradict each other. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Write specific, verifiable instructions ("Use 2-space indentation", "Run `npm test` before committing"); group under headers and bullets; if two instructions contradict, "Claude may pick one arbitrarily". — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Scoping tools: path-scoped rules in `.claude/rules/` with `paths:` frontmatter load only when matching files are touched; subdirectory CLAUDE.md files load on demand; block-level HTML comments are stripped before injection (free notes for human maintainers); `CLAUDE.local.md` holds personal, gitignored preferences. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Rules files are guidance, not enforcement. "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook." CLAUDE.md content is delivered as a user message after the system prompt, with "no guarantee of strict compliance". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] AGENTS.md: Claude Code (v2.1.277+) reads `AGENTS.md` when no CLAUDE.md exists in the working directory or above; to share one file across tools, put `@AGENTS.md` in CLAUDE.md or symlink (`ln -s AGENTS.md CLAUDE.md`; avoid the symlink on Windows). — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [S] Independent evidence that rules files can hurt: "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (Gloaguen, Mündler, Müller, Raychev, Vechev; ETH Zurich; arXiv 2602.11988, Feb 2026; listed at ICLR 2026). Abstract: context files "tend to reduce task success rates compared to providing no repository context, while also increasing inference cost by over 20%". Secondary coverage: LLM-generated files cut success by about 3% on average; developer-written files gave about +4% on AGENTbench at higher step count and cost; architectural overviews did not reduce time spent locating files; authors conclude human-written files "should describe only minimal requirements". The ICLR listing words the result more cautiously as "no improvement". — [arXiv 2602.11988](https://arxiv.org/html/2602.11988); [InfoQ, Mar 2026](https://infoq.com/news/2026/03/agents-context-file-value-review/); [Heise](https://heise.de/-11245317)

Auto memory directory and index (Claude Code)
- [V] Layout: `~/.claude/projects/<project>/memory/` with `MEMORY.md` as "Index, one line per memory, loaded at session start" plus one topic file per memory (examples: `user_role.md`, `feedback_testing.md`). Topic files are not loaded at startup; Claude reads them on demand with ordinary file tools. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Hard cap: "the first 200 lines or 25KB of MEMORY.md, whichever comes first, load at session start. Content beyond that threshold is not loaded." Near the limit the harness reminds Claude to "keep one line per entry, move detail into topic files, and merge or drop stale entries"; over the limit the write succeeds but returns an error telling Claude to rewrite the index. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Dating: when a memory file begins with YAML frontmatter, Claude Code records write time in a `modified` field (ISO 8601): "The timestamp shows how current the fact is, both to you and to Claude when it reads the memory back." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Scope: machine-local, one directory per git repo shared across worktrees; main-conversation memory is not loaded into subagents (subagents can have their own); memory files are excluded from the transcript retention sweep. Plain markdown, user-editable via `/memory`. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [S] A GitHub issue (anthropics/claude-code #25006) reported lines beyond 200 being silently truncated with no warning; the current docs [V] describe a reminder/error mechanism, so the issue likely describes older behaviour. — [GitHub issue](https://github.com/anthropics/claude-code/issues/25006)

Anthropic memory tool (API)
- [V] Client-side file tool (`memory_20250818`), commands `view`, `create`, `str_replace`, `insert`, `delete`, `rename`, all under a `/memories` prefix that the developer maps to real storage. Status: stable; available on all Claude 4+ models. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [V] Auto-injected protocol: "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE ... ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [V] Anti-clutter prompt Anthropic suggests: "when editing your memory folder, always try to keep its content up-to-date, coherent and organized. You can rename or delete files that are no longer relevant. Do not create new files unless necessary." Scope what gets written: "Only write down information relevant to <topic>". — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [V] Operational rules: cap file sizes and cap characters returned by `view` (text view truncates past 16,000 characters; page with `view_range`); "Periodically delete memory files that haven't been accessed in a long time"; validate every path against traversal; strip sensitive data before writing. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [V] Pair memory with compaction/context editing: "compaction keeps the active context small ... and memory preserves the information that must survive summarization." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [V] Vendor-run numbers: on an "internal" agentic search evaluation set, memory tool + context editing improved performance 39% over baseline, context editing alone 29%; in a 100-turn web search evaluation context editing cut token use 84%. Run by Anthropic; methodology not published. — [Claude blog, "Managing context on the Claude Developer Platform", 29 Sep 2025](https://claude.com/blog/context-management)

Managed-agent memory stores (Anthropic, beta)
- [V] Memory store = collection of text documents mounted as a directory under `/mnt/memory/<slug>/`, used with ordinary file tools. Limits: each memory capped at 100 kB (~25k tokens), 10,000 memories per store, max 8 stores per session. "Structure memory as many small focused files, not a few large ones." — [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- [V] Every change creates an immutable memory version (audit trail, point-in-time recovery, `redact` to scrub history); versions retained 30 days; optimistic concurrency via `content_sha256` precondition. — [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- [V] Split stores by owner and access: one read-only shared reference store (standards, domain knowledge) plus a per-user/per-project read-write store. — [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)

Skills as procedural memory
- [V] Three disclosure levels: (1) `name` + `description` of every installed skill preloaded into the system prompt; (2) full `SKILL.md` read when relevant; (3) linked files that Claude "can choose to navigate and discover only as needed". — [Anthropic, "Equipping agents for the real world with Agent Skills", Zhang, Lazuka, Murag, 16 Oct 2025](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- [V] Authoring advice: start from evaluation (find where the agent fails, then write the skill); split SKILL.md when unwieldy and keep mutually exclusive contexts in separate files; make clear whether a script should be run or read; have Claude "capture successful approaches and common mistakes" into the skill. Self-authored skills were stated as a future goal in Oct 2025. — [same post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- [V] "The CLAUDE.md rule applies to skills too: only write down what Claude can't find on its own." Use `disable-model-invocation: true` for skills with side effects. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [S] Rules of thumb from secondary sources: ~100 tokens of metadata per skill; SKILL.md body under ~5,000 tokens; frontmatter `name` max 64 chars, `description` max 1,024 chars. — [agentskills.io](https://agentskills.io/); [Atlan explainer](https://atlan.com/know/ai-agent/ai-agent-skills/skill-md-file-explained/)

Notes / todo / progress files
- [V] Anthropic's long-running harness pattern: an initializer session writes `init.sh`, a progress log, a JSON feature list (all features initially failing) and an initial git commit; every later session runs `pwd`, reads progress notes and git log, reads the feature list, picks one feature, verifies end to end, then commits and updates the progress file. JSON was chosen for the feature list because the model is "less likely to inappropriately change or overwrite JSON files compared to Markdown files"; agents may only flip the `passes` field. — [Anthropic, "Effective harnesses for long-running agents", Justin Young, 26 Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [V] Same pattern restated in the memory tool docs: set up memory files deliberately, "Work on one feature at a time. Mark a feature complete only after end-to-end verification." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [S] Manus ("Context Engineering for AI Agents: Lessons from Building Manus", Yichao "Peak" Ji [B], July 2025 [B]): the file system is treated as the "ultimate context", unlimited, persistent and directly operable by the agent; the agent rewrites a `todo.md` as it works to recite the plan into recent attention (countering goal drift over ~50 tool calls); context is append-only to protect the KV-cache, and tools are masked rather than removed. — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [ZenML summary](https://www.zenml.io/llmops-database/context-engineering-strategies-for-production-ai-agents)

### Inferences
- The convergent structure across Anthropic's three products (Claude Code auto memory, API memory tool, managed memory stores) is: small index always loaded, many small topic files, on-demand reads, versioning, size caps enforced by the harness rather than by the model's good intentions.
- The ETH result and Anthropic's own guidance agree: auto-generated overviews of things the agent can discover by reading the repo are net negative. A memory file should hold only non-derivable knowledge.
- Structured formats (JSON with a single mutable field) are a practical defence against agents rewriting state they should only tick off.

- No independent study was found measuring the 200-line guidance itself; it is a vendor recommendation.

## 3. Karpathy's LLM-maintained wiki and Obsidian-plus-agent "second brain" setups

### Takeaway
Karpathy's April 2026 "LLM Wiki" gist defines the reference pattern: immutable raw sources, an LLM-owned markdown wiki, and a schema file (CLAUDE.md / AGENTS.md) that turns the agent into a disciplined maintainer, with `index.md` and `log.md` as the navigation and history spine. Community Obsidian setups mostly combine this with PARA-style folders and a handful of routine skills; their evidence base is anecdotal.

### Cited Findings
- [V] Three layers: raw sources (curated; the LLM reads but never modifies; "your source of truth"); the wiki (LLM-generated summaries, entity and concept pages, comparisons, synthesis; "You read it; the LLM writes it"); the schema (CLAUDE.md or AGENTS.md defining structure, conventions and workflows, which "is what makes the LLM a disciplined wiki maintainer rather than a generic chatbot"). — [Karpathy, "LLM Wiki" gist, created 4 Apr 2026 (date per search)](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [V] Three operations. Ingest: read a source, discuss takeaways, write a summary page, update the index, revise related entity/concept pages, append to the log; "A single source might touch 10-15 wiki pages"; Karpathy prefers ingesting one source at a time. Query: search the wiki, read pages, answer with citations, and file useful answers back as new pages. Lint: periodic checks for contradictions, stale claims, orphan pages, missing concept pages, missing cross-references and data gaps. — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [V] `index.md`: content-oriented catalogue of every page by category, each with link, one-line summary, optionally date or source count; updated on every ingest and read first on every query. `log.md`: append-only chronological record with a consistent prefix so it is greppable, e.g. `## [2026-04-02] ingest | Article Title`, read with `grep "^## \[" log.md | tail -5`. — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [V] Scale claim: the index approach "works surprisingly well at moderate scale (~100 sources, ~hundreds of pages)" without embedding RAG infrastructure; beyond that he suggests a local search tool such as qmd. The gist is "intentionally abstract" and prescribes no directory tree (only `raw/assets/` for attachments). — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [V] Tooling tips: Obsidian as viewer ("Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase"), graph view to spot hubs and orphans, Obsidian Web Clipper for capture, download images locally, Dataview over frontmatter, Marp for slides, and the wiki is "just a git repo of markdown files". Rationale: "The tedious part of maintaining a knowledge base is not the reading or the thinking — it's the bookkeeping." — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [V] qmd (Tobi Lütke, 31.4k stars): on-device markdown search with BM25, vector search, and a hybrid mode with query expansion, Reciprocal Rank Fusion and LLM re-ranking; CLI plus MCP server; `--json`/`--files` output for agents; per-collection or per-path "context" descriptions returned with matches, which the README calls "the key feature". — [tobi/qmd](https://github.com/tobi/qmd)
- [S] Community implementations follow the gist with a `raw/` folder the AI reads but never writes, e.g. balukosuri/llm-wiki-karpathy; adoption figures not checked. — [GitHub](https://github.com/balukosuri/llm-wiki-karpathy)
- [V] Claudesidian (heyitsnoah / Noah Brier, Alephic; 2.6k stars, MIT): numbered PARA layout `00_Inbox`, `01_Projects`, `02_Areas`, `03_Resources`, `04_Archive`, `05_Attachments`, `06_Metadata` (with `Reference/` and `Templates/`), `.scripts/`. Skills include `inbox-processor`, `daily-review` ("End of day reflection"), `weekly-synthesis` ("Find patterns in your week"), `thinking-partner`, `research-assistant`, `add-frontmatter`. Advice: "Start in thinking mode", "Trust but verify: Always read AI-generated content", "Save everything". — [heyitsnoah/claudesidian](https://github.com/heyitsnoah/claudesidian)
- [S] Kenneth Reitz, "Obsidian Vaults and Claude Code" (essay, 6 Mar 2026): the vault is plain markdown the agent reads and writes directly with no API or middleware. — [kennethreitz.org](https://kennethreitz.org/essays/2026-03-06-obsidian_vaults_and_claude_code)
- [S] Recurring practitioner advice across blog write-ups: the vault-root CLAUDE.md should describe folder structure and naming conventions; one layout uses seven folders around raw sources, a processed subfolder, a wiki, a journal, and index and log files; one write-up warns that deep nesting burns tokens on path resolution and recommends flat layouts. These are blogs and Substack posts, some promotional. — [MindStudio folder architecture](https://www.mindstudio.ai/blog/ai-second-brain-obsidian-vault-folder-architecture); [codemeetai Substack](https://codemeetai.substack.com/p/how-to-build-a-second-brain-with)

### Inferences
- The wiki pattern is a file-based semantic memory with a compile step: retrieval cost is paid at ingest (cross-linking, summarising) rather than at query. That fits a personal or small-team knowledge base and fits poorly where sources change faster than they can be re-ingested.
- The index-first read is the same mechanism as MEMORY.md and skill metadata: a cheap always-readable catalogue that points to detail.
- The main unmeasured risk is error compounding: wiki pages are LLM summaries of sources, and query answers filed back are summaries of summaries. Keeping raw sources immutable and citing them from wiki pages is the stated mitigation; lint is the stated detection step.

- No independent evaluation or critique of LLM-wiki quality at scale was retrieved (search budget exhausted before that query ran).
- The comment thread on the gist is heavy with third-party tool promotion and was excluded; star counts for follow-on repos were not verified apart from Claudesidian and qmd.
- Reitz's essay could not be opened; its specific structure is unknown here.

## 4. Memory frameworks and products; what benchmarks and independent critiques show

### Takeaway
Vendor benchmark numbers are mutually contradictory and largely self-run; LoCoMo in particular is disputed and has been audited as unreliable. The one consistent signal is that simple baselines (files plus agentic search, or retrieval over raw history) are competitive with specialised vector and graph memory on conversational recall, while naive full-context stuffing is not reliably good at long lengths.

### Cited Findings

Letta / MemGPT
- [S] Letta, "Benchmarking AI Agent Memory: Is a Filesystem All You Need?" (12 Aug 2025; run by Letta): LoCoMo histories were placed in files and a Letta agent given file tools scored 74.0% with GPT-4o mini, above Mem0's then-reported 68.5% for its best graph variant. Letta states Mem0 did not respond to requests to clarify its methodology. Letta's argument: LoCoMo measures retrieval, not agentic memory, and agents are already well trained on filesystem tools. — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- [S] Letta, "Sleep-time compute" (research post, 21 Apr 2025): agents use idle time to reorganise information and pre-reason over it; shipped as sleep-time agents in Letta 0.7.0, where a second agent edits the primary agent's memory blocks in the background. — [Letta blog](https://letta.com/blog/sleep-time-compute)
- [S] March 2026 pivot ("Our next phase"): Letta is replacing specialised memory tools that edit a database with general tools (bash) over git-backed files, removing legacy tools such as `core_memory_replace`, and moving sleep-time workflows client-side. — [Letta blog](https://letta.com/blog/our-next-phase)
- [V] Letta Code (3.9k stars, Apache-2.0): "All context (including memory blocks) is tracked via git"; sync to your own repo with `/memory-repository set`; skills load from `~/.letta`, `.agents/skills` and MemFS; sleep-time compute is "now called 'dreaming'", with `/sleeptime`, `/dream` and `/reflect` commands. — [letta-ai/letta-code](https://github.com/letta-ai/letta-code)
- [S] MemFS is on by default for new agents in Letta Code 0.15+; Docker-server agents still use memory blocks. A third-party review described the git-backed system as still early. — [Letta docs](https://docs.letta.com/letta-code/memfs); [zby review](https://zby.github.io/commonplace/agent-memory-systems/reviews/letta/)

Mem0
- [V] Mem0 (69.4k stars, Apache-2.0). New algorithm, April 2026: "Single-pass ADD-only extraction" (one LLM call, no UPDATE or DELETE; memories accumulate rather than being overwritten); retrieval fuses semantic search, BM25 and entity matching. — [mem0ai/mem0 README](https://github.com/mem0ai/mem0)
- [V] Self-reported scores (run by Mem0, on its managed platform with "proprietary optimizations"; open-source users told to expect "directionally similar gains but not identical numbers"): LoCoMo 71.4 -> 92.5, LongMemEval 67.8 -> 94.4, BEAM-1M 64.1, BEAM-10M 48.6, at ~7K tokens and ~1 s p50 per query. Harness published at mem0ai/memory-benchmarks; no independent evaluator named. — [mem0ai/mem0 README](https://github.com/mem0ai/mem0)
- [S] Mem0 says its own LoCoMo figures of 74% and 92.5% reflect different setups; Letta has not rerun the filesystem experiment against the new pipeline. — [Mem0, "How to read memory benchmarks"](https://mem0.ai/library/agent-memory/how-to-read-memory-benchmarks); [Towards AI article](https://pub.towardsai.net/mem0-vs-zep-vs-letta-a-folder-of-text-files-shouldnt-beat-the-61k-star-memory-layer-9d7e65c5799c)

Zep / Graphiti
- [S] Paper: "Zep: A Temporal Knowledge Graph Architecture for Agent Memory" (Rasmussen et al., Zep AI, arXiv 2501.13956, 20 Jan 2025). Bi-temporal model: one timeline for when events happened and one for when data was ingested; updates are non-lossy with validity periods. Vendor-run results: 94.8% vs MemGPT's 93.4% on DMR, plus LongMemEval. — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956v1)
- [V] Graphiti (33.0k stars): "Explicit bi-temporal tracking with automatic fact invalidation"; superseded facts are invalidated but kept; hybrid retrieval over embeddings, BM25 and graph traversal; needs a graph backend (Neo4j, FalkorDB, Neptune) and LLM calls at ingest for entity/edge extraction and deduplication; the reference MCP server "has no authentication or prompt-injection protection". — [getzep/graphiti](https://github.com/getzep/graphiti)
- [S] LoCoMo dispute: Mem0's paper reported Zep at 65.99%; Zep replied ("Lies, Damn Lies, Statistics: Is Mem0 Really SOTA in Agent Memory?") claiming 84% with correct configuration (parallel searches, timestamps in `created_at`); Mem0's CTO filed an issue, Zep conceded an error and published a corrected 75.14% ±0.17, while Mem0's rerun of the same code gave 58.44% ±0.20. Both sides are vendors; the figures remain unreconciled. — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/); [Atlan comparison](https://atlan.com/know/zep-vs-mem0/)
- [S] LongMemEval: Mem0 reports Mem0 93.4 vs Zep 71.2 (GPT-4o); another comparison cites Zep at 90.2% with a different reader and judge model. Both vendors self-report on configurations neither fully discloses. — [Mem0 benchmarks blog](https://mem0.ai/blog/ai-memory-benchmarks); [Atlan comparison](https://atlan.com/know/zep-vs-mem0/)

Cognee and LangMem
- [V] Cognee (33.5k stars): "the open-source AI memory platform for agents"; turns documents, code and conversations into a self-hosted knowledge graph plus searchable chunks; four operations `remember`, `recall`, `improve`, `forget`; self-reported BEAM scores 0.79 at 100K and 0.67 at 10M tokens, with the README's own warning that the two settings are not directly comparable. — [topoteretes/cognee](https://github.com/topoteretes/cognee)
- [S] LangChain's memory guidance (semantic / episodic / procedural; hot path vs background) is the conceptual basis for LangMem; no LangMem-specific material was surfaced. — [LangChain memory docs](https://docs.langchain.com/oss/python/concepts/memory)

ChatGPT and Claude consumer memory
- [S] Simon Willison, "I really don't like ChatGPT's new memory dossier" (21 May 2025): objects to an opaque, automatically built user profile injected into every chat; example of contamination, an unrequested "Half Moon Bay" sign in a generated image because he had mentioned the place before. — [simonwillison.net](https://simonwillison.net/2025/May/21/chatgpt-new-memory/)
- [S] Willison's 12 Sep 2025 link post on Shlok Khemani's analysis: Claude starts each conversation from "a blank slate" with no preloaded profile and retrieves past chats via explicit tool calls; Claude's memory summary is user-visible and editable, which Willison says addresses his main complaint about ChatGPT memory. — [simonwillison.net](https://simonwillison.net/2025/Sep/12/claude-memory/)
- [S] Secondary characterisation: Claude's memory is a categorised wiki-like document; ChatGPT's accumulates as a flat list. — [MindStudio comparison](https://www.mindstudio.ai/blog/claude-memory-vs-chatgpt-memory-comparison)

Benchmark validity and independent work
- [S] Penfield Labs audit of LoCoMo: part of the answer key is wrong (the URL slug reads "64", most likely 6.4%; exact figure not confirmed from the page) and the LLM judge accepts up to 63% of intentionally wrong answers; multiple researchers could not reproduce published results; LoCoMo and LongMemEval-S (~115K tokens per question) do not isolate memory from context-window capacity. Penfield builds memory tooling, so it is third-party to the disputes but not disinterested. — [Penfield Labs on DEV](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)
- [S] On Mem0's own early table, a plain full-context baseline scored about 73% on LoCoMo against about 68% for Mem0's best variant. — [Towards AI article](https://pub.towardsai.net/mem0-vs-zep-vs-letta-a-folder-of-text-files-shouldnt-beat-the-61k-star-memory-layer-9d7e65c5799c)
- [S] "Do Conversational Agents Need Explicit Memory? A Controlled Comparison with Raw-History Retrieval" (arXiv 2610.24671, Oct 2026): full-context scored 22.2 on LongMemEval-S and 24.4 on BEAM-100K, while raw-history retrieval scored between 56 and 78; the answer generator capped context at 138K tokens, which may depress the full-context figure. — [arXiv 2610.24671](https://arxiv.org/pdf/2610.24671)
- [S] "MemDelta: Controlled Baselines and Hidden Confounds in Agent Memory Evaluation" (arXiv 2606.29914, June 2026) exists as a paper on confounds in memory evaluation; contents not retrieved. — [arXiv 2606.29914](https://arxiv.org/pdf/2606.29914)
- [S] MemoryAgentBench ("Evaluating Memory in LLM Agents via Incremental Multi-Turn Interactions", arXiv 2507.05257; ICLR 2026) tests four competencies across memory agents and long-context agents and finds existing memory agents "still face significant challenges". BEAM evaluates at up to 10M+ tokens. — [arXiv 2507.05257](https://arxiv.org/html/2507.05257v3); [Mem0 benchmark overview](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)
- [S] An open harness, memtrust, aims at cross-vendor runs but had only one backend fully run; a separate project's claimed 100% LongMemEval score was irreproducible and withdrawn. — [memtrust on Socket](https://socket.dev/pypi/package/memtrust-cli)

### Inferences
- Is plain files plus search competitive? On conversational-recall benchmarks, yes within the error bars of the benchmarks themselves: Letta's file agent (74%) beat the Mem0 number of the day, and raw-history retrieval is a strong baseline in the one controlled comparison found. The later 90%+ vendor scores have not been independently reproduced, and the main benchmark's answer key and judge are themselves in question.
- The market converged on files during 2025-2026: Letta moved from database memory blocks to git-backed files, Anthropic shipped three file-shaped memory products, and Mem0 dropped UPDATE/DELETE in favour of append-only accumulation. Specialised stores now justify themselves on scale, latency, multi-tenant serving and temporal queries rather than on recall accuracy.
- Graph memory's distinctive, defensible feature is temporal validity (what was true when), not higher benchmark scores.

### Gaps
- No vendor-neutral head-to-head of Mem0, Zep, Letta and a file baseline on the same harness was found.
- ChatGPT memory internals (saved memories vs chat-history reference, how they are injected) were not retrieved this session.
- Details of arXiv 2610.24671 and MemDelta (authors, systems compared, conclusions) are unverified; arxiv.org was unreachable.
- Outdated material to discount: Mem0's 2025 LoCoMo table and the 68.5%/65.99% figures (superseded and disputed); MemGPT-era `core_memory_*` tool designs (being removed by Letta); DMR benchmark results (small and saturated at ~94%).

## 5. Retrieval: agentic search vs embeddings RAG vs knowledge graphs

### Takeaway
For corpora an agent can browse (code, notes, a memory directory), leading practitioners prefer agentic search with file tools plus an always-loaded index, adding hybrid BM25/vector search only when the corpus outgrows the index. Graphs earn their cost for relational and time-dependent questions.

### Cited Findings
- [V] Just-in-time retrieval: agents keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load data at runtime with tools; Claude Code uses targeted queries and commands like `head` and `tail` rather than loading whole data objects. — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [V] Progressive disclosure: agents "incrementally discover relevant context through exploration", each step informing the next. Hybrid strategy: load some data up front for speed (CLAUDE.md is "naively dropped into context up front") and explore the rest on demand; suggested for less dynamic domains such as legal or finance. — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [V] "Memory supports just-in-time context retrieval. Rather than loading all relevant information up front, an agent records what it learns in memory files and reads them back on demand." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [S] Boris Cherny (creator of Claude Code): "Early versions of Claude Code used RAG + a local vector database, but we found pretty quickly that agentic search generally works better. It outperformed everything, by a lot." Pragmatic Engineer's interview summary: agentic search "is really just glob and grep"; vector databases and recursive model-based indexing were tried and dropped, with stale indexes and permission complexity among the drawbacks. Evidence is the vendor's internal experience, not a published benchmark. — [Pragmatic Engineer, "Building Claude Code with Boris Cherny"](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny)
- [S] Letta attributes its file-agent result to models being heavily trained on filesystem tools, so iterative search with familiar tools beats a bespoke retrieval API. — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- [V] Karpathy: an index file suffices at ~100 sources / hundreds of pages; past that, add local hybrid search (qmd: BM25 + vector + LLM re-rank, exposed over CLI or MCP). — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f); [tobi/qmd](https://github.com/tobi/qmd)
- [V] Vendor memory layers have moved to hybrid retrieval: Mem0 fuses semantic, BM25 and entity matching in a single pass; Graphiti combines embeddings, BM25 and graph traversal and reports typically sub-second queries versus seconds to tens of seconds for batch GraphRAG. — [mem0ai/mem0](https://github.com/mem0ai/mem0); [getzep/graphiti](https://github.com/getzep/graphiti)
- [S] A talk at AI Engineer benchmarked semantic code retrieval on Claude; content not retrieved. — [ai.engineer talk listing](https://ai.engineer/talks/zKk7sDMGDEQ-benchmarking-semantic-code-retrieval-on-claude)

### Inferences
- Agentic search trades latency and tokens (several tool calls per lookup) for freshness and zero index maintenance. Single-pass vector retrieval trades the reverse. Mem0's ~1 s / ~7K-token figure and a multi-step grep loop are not competing on the same axis.
- Pure keyword search fails when the query vocabulary differs from the stored wording; this is what the index file (one-line summaries), qmd's query expansion and collection "context" descriptions compensate for.
- A sensible escalation path: index file -> grep/glob -> local hybrid search -> graph, moving up only when the previous level demonstrably fails.

### Gaps
- No public controlled benchmark of grep-style agentic search versus embeddings for memory (as opposed to code) was retrieved beyond the Letta post and arXiv 2610.24671.
- Cursor's and other IDE vendors' counter-evidence in favour of semantic indexing was not searched.

## 6. Memory maintenance: consolidation, forgetting, provenance, staleness, privacy and injection

### Takeaway
Memory degrades by accumulation: duplicates, contradictions and stale entries build up because writes are local and incremental. The current answer is a scheduled offline consolidation pass ("dreaming" / sleep-time) that produces a reviewable new version, combined with dated entries, size caps, version history, and treating memory as an untrusted-input sink.

### Cited Findings
- [V] Anthropic's statement of the problem: agent writes "are local and incremental: over many sessions a memory store accumulates duplicates, contradictions, and stale entries." — [Managed agents, Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)
- [V] Dreams (research preview; beta header `dreaming-2026-04-21`): an asynchronous job takes one memory store plus 1-100 past session transcripts and produces a new, separate store with "duplicates merged, stale or contradicted entries replaced with the latest value, and new insights surfaced". "The input store is never modified, so you can review the output and discard it." Steerable with instructions such as "Focus on coding-style preferences; ignore one-off debugging notes"; runs take minutes to hours; cost scales roughly linearly with transcripts; "Start with a small batch of sessions". — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)
- [S] Claude Code "auto dream" / `/dream`, per third-party write-ups only (not found in the official memory docs read this session): four phases, orient (survey memory), gather signal (find drifted facts), consolidate (merge duplicates, fix dates, delete contradictions), prune (rebuild MEMORY.md under 200 lines); reported trigger of at least 24 hours and at least 5 sessions since the last run; reported server-side flag rollout; one guide says each run writes a `.bak` and advises against running mid-task. — [finisky write-up](https://finisky.github.io/en/claude-code-auto-dream); [MindStudio explainer](https://www.mindstudio.ai/blog/what-is-claude-code-autodream-memory-consolidation); [community plugin jl-cmd/claude-dream](https://github.com/jl-cmd/claude-dream)
- [S] Letta's sleep-time compute (Apr 2025) is the earlier formulation: a background agent reorganises memory during idle time; now run client-side as "dreaming" subagents that reflect on recent conversations. — [Letta blog](https://letta.com/blog/sleep-time-compute); [Letta docs](https://docs.letta.com/letta-code/memory/index.md)
- [V] Karpathy's "lint" is the wiki equivalent: periodic checks for contradictions, stale claims, orphans, missing cross-references and gaps. — [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [V] Forgetting and expiry: "Periodically delete memory files that haven't been accessed in a long time"; cap file sizes; Claude Code's index cap forces merging or dropping stale entries. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Provenance and dating: Claude Code stamps a `modified` ISO 8601 field in memory frontmatter; managed memory stores keep immutable versions attributed to the writing session; Graphiti keeps provenance to source episodes and validity windows, invalidating rather than deleting superseded facts. — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory); [getzep/graphiti](https://github.com/getzep/graphiti)
- [V] Two opposite policies for contradictions exist in shipping systems: overwrite with the latest value (Anthropic Dreams), or never overwrite and resolve at read time (Mem0's April 2026 ADD-only extraction; Graphiti's invalidate-but-keep edges). — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams); [mem0ai/mem0](https://github.com/mem0ai/mem0); [getzep/graphiti](https://github.com/getzep/graphiti)
- [V] Prompt-injection risk stated by Anthropic: "If the agent processes untrusted input (user-supplied prompts, fetched web content, or third-party tool output), a successful prompt injection could write malicious content into the store. Later sessions then read that content as trusted memory. Use `read_only` for reference material, shared lookups, and any store the agent does not need to modify." — [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- [S] Research on memory poisoning: MINJA ("Memory Injection Attacks on LLM Agents via Query-Only Interaction", arXiv 2503.03704) injects through ordinary queries without direct memory access, with reported >95% injection success and ~70% attack success under idealised conditions. A June 2026 systematic study ("From Untrusted Input to Trusted Memory", arXiv 2606.04329) finds prompt-injection defences leave gaps because a poisoned memory may carry no detectable instruction pattern, and that a single successful write suffices. Sleeper-style payloads are reported to stay dormant and re-emerge across later conversations, in one study after 100 benign sessions. — [arXiv 2503.03704](https://arxiv.org/html/2503.03704v5); [arXiv 2606.04329](https://arxiv.org/pdf/2606.04329); [arXiv 2601.05504](https://arxiv.org/pdf/2601.05504)
- [V] Supply-chain variant: skills and shared rule files are memory other people can write. Anthropic: "We recommend installing skills only from trusted sources" and audit bundled files and scripts; Claude Code shows an approval dialog for imports that resolve outside the working directory "to protect you from files other people commit to a shared project". — [Agent Skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills); [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- [V] Privacy controls: the model "usually refuses to write sensitive information to memory files. For stronger guarantees, add validation that strips sensitive data before your handler writes"; managed stores offer `redact` on version history; managed-agent memory is not ZDR-eligible, while the client-side memory tool is. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- [S] User-facing transparency as a design requirement: Willison's objection to ChatGPT's "dossier" is that the user cannot inspect what is injected and that memory leaks into unrelated tasks; he credits Claude's visible, editable summary. — [simonwillison.net, May 2025](https://simonwillison.net/2025/May/21/chatgpt-new-memory/); [simonwillison.net, Sep 2025](https://simonwillison.net/2025/Sep/12/claude-memory/)

### Inferences
- A workable maintenance loop, assembled from the sources: (1) write small dated entries during work; (2) consolidate offline against raw transcripts on a schedule; (3) emit the result as a new version or a diff, never an in-place rewrite; (4) have a human or a second check review it; (5) keep raw transcripts and sources immutable so consolidation errors are recoverable.
- Consolidation is itself lossy summarisation by a model. Anthropic's non-destructive output store and Letta's git history are both acknowledgements of that; a setup without versioning should not run automatic consolidation.
- Memory raises the severity of prompt injection from one session to all future sessions. The practical controls are structural: separate read-only reference memory from writable memory, do not let sessions that read untrusted content write to shared memory unreviewed, and keep an audit trail.

### Gaps
- No official Anthropic documentation of Claude Code's auto-dream was found in the pages read; all details are third-party.
- Johann Rehberger's SpAIware work on ChatGPT memory exfiltration was not surfaced by search and is not cited here.
- No quantitative evidence was found on how much consolidation improves downstream task success, from any vendor.

### Takeaway
Five published setups are specific enough to copy: Claude Code's own memory layout, Anthropic's long-running-agent harness, Karpathy's LLM Wiki, Claudesidian for Obsidian, and Letta Code's git-backed memory. All are plain files in git.

### Cited Findings

### Gaps

- Business-team setups (shared wikis maintained by agents across several people) are thinly documented outside vendor docs.

## 8. Comparison of approaches: what to use when, and known failure modes

### Takeaway
Start with files and agentic search; add hybrid search when the index stops fitting; adopt a vector memory service for high-volume multi-user personalisation and a temporal graph only when "what was true when" and entity relations are core requirements. Every approach fails by silent accumulation unless size caps, dating, versioning and review are built in.

### Cited Findings

| Approach | Use when | Known failure modes | Evidence |
|---|---|---|---|
| Rules file (CLAUDE.md / AGENTS.md), always loaded | Small set of non-derivable project rules and commands | Bloat lowers adherence; contradictions resolved arbitrarily; LLM-generated files reduce task success and add >20% cost; not enforced | [V] [Claude Code memory docs](https://code.claude.com/docs/en/memory); [S] [arXiv 2602.11988](https://arxiv.org/html/2602.11988) |
| Hooks / deny rules | Anything that must happen every time | Over-use: each rule misfires occasionally and needs maintenance | [V] [Claude Code best practices](https://code.claude.com/docs/en/best-practices) |
| Skills (procedural memory) | Multi-step team procedures used occasionally | Poor `description` means the skill never triggers; untrusted skills are an injection and exfiltration vector | [V] [Agent Skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) |
| Memory directory + index + topic files | Single agent or single user; preferences, corrections, project facts | Index overflow past 200 lines / 25 KB is not loaded; duplicates and stale entries accumulate; machine-local | [V] [Claude Code memory docs](https://code.claude.com/docs/en/memory); [V] [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams) |
| Progress / todo / feature-list files | Long tasks across context resets | Agent marks work done without verification; agent rewrites the checklist (mitigate with JSON and a single mutable field) | [V] [Long-running harness post](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) |
| LLM-maintained wiki | Personal or small-team knowledge base, ~100 sources / hundreds of pages | Index stops scaling; contradictions, stale claims and orphans without lint; summaries of summaries | [V] [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) |
| Agentic search over raw files / transcripts | Corpora that change often; code; moderate size | More tool calls and latency per lookup; vocabulary mismatch for keyword search | [S] [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny); [S] [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory) |
| Vector / hybrid memory service (Mem0 and similar) | Many users, low latency, single-pass retrieval at ~7K tokens | Extraction loses detail; benchmark claims self-run and disputed; managed scores not reproducible on open source | [V] [mem0ai/mem0](https://github.com/mem0ai/mem0); [S] [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/) |
| Temporal knowledge graph (Zep / Graphiti, Cognee) | Facts that change over time, entity-relation queries, audit of when something was believed | Graph database to operate; LLM calls on every ingest; extraction and deduplication errors; unauthenticated reference MCP server | [V] [getzep/graphiti](https://github.com/getzep/graphiti); [V] [topoteretes/cognee](https://github.com/topoteretes/cognee) |
| Full-context stuffing | Short histories only | Context rot; scored 22-24 where retrieval scored 56-78 in one controlled study (with a 138K cap caveat) | [V] [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [S] [arXiv 2610.24671](https://arxiv.org/pdf/2610.24671) |
| Opaque auto-profile injected into every chat (ChatGPT-style) | Consumer personalisation | Not inspectable; bleeds into unrelated tasks | [S] [simonwillison.net](https://simonwillison.net/2025/May/21/chatgpt-new-memory/) |
| Scheduled consolidation ("dreaming") | Any memory that has run for many sessions | Lossy rewrite; needs review and versioning; cost linear in transcripts | [V] [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams) |

Cross-cutting failure modes with sources:
- Memory poisoning persists across sessions after a single successful write. — [S] [arXiv 2606.04329](https://arxiv.org/pdf/2606.04329); [V] [Managed agents memory docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Benchmarks do not settle product choice: LoCoMo's key and judge are disputed, and vendors report incompatible numbers for each other. — [S] [Penfield Labs audit](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg); [S] [Atlan comparison](https://atlan.com/know/zep-vs-mem0/)

### Inferences
- For a solo developer or a personal knowledge base, nothing in the evidence justifies starting with a vector or graph store. The file stack is cheaper, inspectable, versionable in git, and matches where Anthropic and Letta have both landed.
- For a business product serving many end users, the deciding factors are latency, tenancy, audit and data-retention rules, where managed stores or a memory service fit better than a shared folder.
- Whatever the store, the durable asset is the raw record (transcripts, sources). Derived memory can be rebuilt from it; the reverse is not true.

### Gaps
- Cost comparisons (tokens and latency per answered question) across file-based, vector and graph memory on one workload were not found from a neutral source.
- No evidence was found on memory quality over horizons longer than benchmark conversations (months of real use).
