## What does each recommend about harness design, instruction files and repo documentation, verification, long-running autonomy, multi-agent scaling, memory and tools?

### Takeaway
The builders converge on a small set of practices: keep the always-loaded instruction file short and use it as a map to versioned repo docs, turn rules into executable checks (linters, tests, review agents) instead of prose, let the agent run and observe the real app, keep durable state in files and git instead of in the context window, and prefer simple role structures (planner plus isolated workers, or no orchestrator at all) over elaborate coordination. They differ sharply on how much human review, gating and multi-agent hierarchy is needed (see the third question).

#### Ryan Lopopolo (OpenAI Frontier at time of writing; harness engineering, Symphony)
- Core claim: the engineer's job shifts from writing code to designing environments, specifying intent and building feedback loops so Codex can do reliable work; early progress was slow "not because Codex was incapable, but because the environment was underspecified" — [OpenAI](https://openai.com/index/harness-engineering/) [search]
- Instruction files: the team abandoned one large AGENTS.md; AGENTS.md is treated as "the table of contents", not the encyclopedia (about 100 lines per secondary summaries), pointing into a structured `docs/` directory that is the system of record (ARCHITECTURE.md, DESIGN.md, PLANS.md, QUALITY_SCORE.md, RELIABILITY.md, core-beliefs.md, tech-debt-tracker.md, an index) — [OpenAI](https://openai.com/index/harness-engineering/) [search]
- Reasons given for dropping the big file: context is scarce, "too much guidance becomes non-guidance", a monolith rots and cannot be mechanically verified; knowledge in Slack or Google Docs "doesn't exist" for the agent unless it is in the repo; plans are checked in as versioned execution plans — [OpenAI](https://openai.com/index/harness-engineering/) [bg]
- Doc upkeep: a recurring "doc-gardening" agent finds docs that no longer match code and opens fix-up PRs (secondhand wording) — [Augment summary](https://www.augmentcode.com/guides/harness-engineering-ai-coding-agents) [search]
- Enforcement: architecture is mechanically enforced with custom linters and structural tests over a fixed layer ordering; lint error messages are written to carry remediation instructions into the agent's context; "boring", well-documented technology is preferred and small library subsets are sometimes reimplemented so the agent can fully see them — [OpenAI](https://openai.com/index/harness-engineering/) [bg; "mechanically enforced architecture" corroborated by search]
- Verification by operating the real system: Chrome DevTools Protocol wired into the agent runtime with skills for DOM snapshots, screenshots and navigation so Codex reproduces bugs and validates fixes; the app boots once per git worktree with an ephemeral per-worktree observability stack (logs, metrics, traces) the agent can query — [OpenAI](https://openai.com/index/harness-engineering/) [search]; [AI Engineer talk](https://ai.engineer/talks/am_oeAoUhew-harness-engineering) [search]
- Review: almost all review is agent-to-agent; persona-based review sub-agents (e.g. frontend architect, reliability engineer, appsec engineer persona docs) run on push; the implementing agent may acknowledge, defer or reject feedback; "Most of the human review is post merge at this point"; native-app releases still needed a human-approved smoke test — [Latent Space](https://latent.space/p/harness-eng) [search]; [Latent Space wiki](https://latent.space/wiki/ryan-lopopolo/) [search]
- Feedback into infrastructure: "I never want to give the same review feedback twice"; a weekly routine converts repeated review comments into docs, checks and reviewer agents; "Everything I've talked about here today is a prompt" (lint messages, review agents, skills) — [AI Engineer talk](https://ai.engineer/talks/am_oeAoUhew-harness-engineering) [search]
- Entropy control ("garbage collection"): background Codex tasks scan for drift from the rules, update quality grades and open small refactoring PRs, most reviewable in under a minute; originally the team spent Fridays (about 20% of the week) cleaning up "AI slop", which did not scale, so "golden principles" were encoded and cleanup automated — [secondary summaries](https://www.agentastic.dev/harness-engineering) [search]; Friday/20% and "golden principles" detail [bg] from [OpenAI](https://openai.com/index/harness-engineering/)
- Merge philosophy: minimal blocking merge gates and short-lived PRs; in a high-throughput agent system "corrections are cheap, and waiting is expensive" — [OpenAI](https://openai.com/index/harness-engineering/) [bg]
- Skills: leverage is concentrated in roughly five to ten skills with clear contracts, not a large catalog (secondary framing) — [AI Engineer talk](https://ai.engineer/talks/am_oeAoUhew-harness-engineering) [search]
- His 12 theses (repo thesis index): hold the worker (model + agent) constant and improve context/tools; deploy into the organization's private process data; give one agent the whole job (decomposition, execution, proof, safe closure); route context just in time (large store, small working set); make capabilities legible (discover, select, invoke, interpret, repair, verify); make the repository teach the agent; maximize autonomy inside explicit authority (separate capability from authority); prove the outcome in the real environment ("a passing check proves only what it asserts"); turn feedback into infrastructure; preserve coherence and own lifetime risk; run known work as a continuous loop; optimize for useful outcomes per unit of scarce human attention, "not tokens, lines, agents, or checks" — [lopopolo/harness-engineering docs](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/README.md) [page]
- His own AGENTS.md models the practice: read the target repo's instructions and real tools/tests first; name the open decision; load only the one thesis that addresses it; local truth overrides general guidance; adapt, don't copy file layouts; verify with native checks and user journeys — [AGENTS.md](https://github.com/lopopolo/harness-engineering/blob/trunk/AGENTS.md) [page]
- Symphony: an orchestrator that turns a Linear board into a control plane; each open issue maps to a dedicated isolated agent workspace; agents supply proof of work (CI status, PR review feedback, complexity analysis, walkthrough videos) and land the PR; "works best in codebases that have adopted harness engineering"; shipped as a spec plus an experimental Elixir reference implementation, labelled "a low-key engineering preview for testing in trusted environments" — [openai/symphony](https://github.com/openai/symphony) [page]
- Symphony spec design: it is "a scheduler/runner and tracker reader", not a ticket editor; a repo-owned `WORKFLOW.md` (YAML front matter + prompt template, strict rendering, hot reload, last-known-good on invalid edit); one orchestrator owns scheduling state; per-issue workspace directories; global and per-state concurrency limits; exponential backoff from 10 s capped at 5 min; stalled sessions killed and retried; recovery from tracker + filesystem state; approval prompts must never stall a run indefinitely; "Human Review" handoff counts as success; tracker secrets stay host-side — [SPEC.md](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md) [page]

#### Michael Bolin and the Codex team
- The harness is the agent loop coordinating user, model and tools; a turn always ends with an assistant message, which is the termination signal; inference runs over the Responses API — [OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop) [search]
- Codex keeps requests stateless (no `previous_response_id`) to stay simple for providers and to support Zero Data Retention; the cost of resending history is contained by exact-prefix prompt caching, so static content (instructions, tool definitions) goes first and the prompt is only appended to — [InfoQ](https://www.infoq.com/news/2026/02/codex-agent-loop) [search]
- Cache-miss hazards named in the post: changing the tool list mid-conversation, switching model, changing sandbox/approval settings or cwd; Codex appends a new message describing the change instead of editing earlier ones; an MCP tool-ordering inconsistency was cited as a real cache bug — [OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop) [bg]
- Compaction: past a token threshold (`auto_compact_limit`) Codex calls a dedicated `/responses/compact` endpoint that returns a shorter item list carrying an opaque encrypted item preserving the model's latent understanding (secondary sources differ slightly on the shape) — [Codex CLI internals survey](https://yage.ai/share/codex-cli-internals-survey-en-20260314.html) [search]
- AGENTS.md handling: files are discovered from the Git root down to the cwd and aggregated into a user-role message under a 32 KiB default limit (whether per-file or total is disputed between secondary sources) — [Codex agent loop explainer](https://codex.danielvaughan.com/2026/04/18/codex-cli-agent-loop-explained/) [search]
- App Server: the same harness is exposed over a bidirectional JSON-RPC API; shell and file tools run in a sandbox, and MCP servers and skills join the loop under one policy model — [OpenAI](https://openai.com/index/unlocking-the-codex-harness) [search]
- DevDay 2026 (2026-09-29): Dots (persistent agents for ongoing tasks) and ChatGPT Space (shared workspace); Agents API gains computer use and a managed Codex harness that handles sessions, orchestration, context compaction and recovery while developers supply tools and execution environments; Codex CLI gains voice input and an `/agents` interface for delegating and monitoring multiple tasks; automatic code reviews; reusable cloud environments; a Decisions API in limited preview — [InfoQ](https://www.infoq.com/news/2026/10/openai-devday-2026/) [search]; [OpenAI recap](https://openai.com/index/devday-2026-recap/) [search]

#### Wilson Lin and Cursor
- Failed design 1: flat, self-coordinating agents sharing a coordination file with locks; agents held locks too long, forgot to release them, crashed holding them or wrote without them; "twenty agents produced the throughput of two or three" — [DEV write-up of Cursor posts](https://dev.to/aiengillustrated/how-cursor-got-thousands-of-ai-agents-to-build-one-browser-3loh) [search]
- Failed design 2: optimistic concurrency removed lock contention, but with no hierarchy agents became risk-averse, avoided hard tasks and nobody owned end-to-end work — [Cursor](https://cursor.com/blog/scaling-agents) [bg; "risk-averse" corroborated by search summary]
- Working design (Jan 2026): planners continuously explore the codebase and create tasks and can spawn sub-planners; workers "don't coordinate with other workers or worry about the big picture"; a judge decided at the end of each cycle whether to continue — [Cursor](https://cursor.com/blog/scaling-agents) [search]
- Revised design (Feb 2026): the judge was removed ("agents were reasonably good at following instructions to completion"); a merged "continuous executor" misbehaved (slept randomly, stopped spawning, did the work itself, claimed premature completion); the central integrator / merge gate was deleted as "red tape" (hundreds of workers, one gate); final shape is a root planner that "does no coding itself", recursive sub-planners owning slices of scope, and isolated workers that are "solely responsible" for a task and return a single written handoff to the planner that asked — [Cursor](https://cursor.com/blog/self-driving-codebases) [search]
- Correctness policy: requiring 100% correctness before every commit caused serialization and throughput collapse; the system accepts a small error rate that "remains small and constant" and is fixed forward — [Cursor](https://cursor.com/blog/self-driving-codebases) [search]
- Prompting lessons: unclear instructions made agents do low-value work and pick designs that could not grow; don't instruct for what models already know; treat the model like a skilled new hire; add summarization at context limits and self-reflection prompts — [Cursor](https://cursor.com/blog/self-driving-codebases) [search]
- Further prompting detail I recall but could not re-confirm: constraints work better than instructions (e.g. "no TODOs, no partial implementations"), and concrete numeric scope beats vague scope — [Cursor](https://cursor.com/blog/self-driving-codebases) [bg, unconfirmed this session]
- Model choice per role: GPT-5.2 held focus over long runs better than alternatives; each role now uses the best-suited model; periodic fresh starts are still needed against drift and tunnel vision — [Cursor](https://cursor.com/blog/scaling-agents) [search]
- Infrastructure lesson: hundreds of agents compiling a monolithic project produced many GB/s of build-artifact disk I/O — [DEV write-up](https://dev.to/aiengillustrated/how-cursor-got-thousands-of-ai-agents-to-build-one-browser-3loh) [search]
- Product form: long-running agents "propose a plan and wait for approval instead of immediately jumping into execution" (upfront alignment in place of mid-run steering) — [Cursor](https://cursor.com/blog/long-running-agents) [search]

#### Kenton Varda and Sunil Pai (Cloudflare)
- Thesis: "we've all been using MCP wrong"; agents handle more and more complex tools when the tools are presented as a TypeScript API and the model writes code against it, because LLMs have seen real code from millions of projects but few tool-call transcripts; Varda's analogy is asking Shakespeare to take a crash course in Mandarin and then write a play in it — [Cloudflare](https://blog.cloudflare.com/code-mode/) [search]
- Second argument: with direct tool calls every intermediate result passes back through the model; code composes calls and returns only the final result — [Cloudflare](https://blog.cloudflare.com/code-mode/) [bg]
- MCP is kept, not discarded: Varda credits MCP with being "very clear about auth" compared with OpenAPI's many auth mechanisms — [Kenton Varda on X](https://x.com/KentonVarda/status/1987208904724652273) [search]
- Sandbox: generated code runs in a Dynamic Worker isolate; external `fetch()`/`connect()` are blocked by default (`globalOutbound: null`); "Sandboxed code can only interact with the host through namespaced tool calls"; credentials stay in the host; tools can be marked `requiresApproval`; package is "Experimental" — [codemode README](https://github.com/cloudflare/agents/blob/main/packages/codemode/README.md) [page]
- Two patterns in Cloudflare docs: a single code tool for a manageable toolset, and `search()` + `execute()` over an OpenAPI spec for very large APIs, separating capability discovery from authenticated calls — [Cloudflare docs](https://developers.cloudflare.com/agents/model-context-protocol/codemode/) [search]
- Agents SDK direction (Project Think, April 2026 preview): durable execution with fibers (crash recovery, checkpointing, keepalive); isolated sub-agents each with their own SQLite and typed RPC; persistent tree-structured sessions with branching, compaction and full-text search; sandboxed code execution; agents as Durable Object actors that sleep until an event arrives — [Cloudflare](https://blog.cloudflare.com/project-think/) [search]; [InfoQ](https://infoq.com/news/2026/04/cloudflare-project-think) [search]

#### Sarah Wooders and Charles Packer (Letta)
- Memory is a context-management problem: "memory is more about how agents manage context than the exact retrieval mechanism used"; a plain agent with conversation history stored as files beat a specialized memory product on LoCoMo — [Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory/) [search]
- Context Repositories (MemFS): agent memory is a git-backed directory of markdown files; every memory change is a commit with an informative message; sub-directories with their own index stay out of context until needed (progressive disclosure); each memory subagent gets an isolated git worktree and merges back via git conflict resolution; on by default from Letta Code 0.15 — [Letta](https://letta.com/blog/context-repositories) [search]; [Letta docs](https://docs.letta.com/letta-code/memfs) [search]
- Sleep-time compute, now called "dreaming": background agents rewrite raw context into learned context while the main agent is idle; `/sleeptime`, `/dream`, `/reflect`, `/doctor` commands; "All context (including memory blocks) is tracked via git"; agents "learn and evolve over long horizons through rewriting their own memory, skills, prompts, and even the harness itself" — [Letta Code README](https://raw.githubusercontent.com/letta-ai/letta-code/HEAD/README.md) [page]
- Continual learning in token space: agents should actively maintain and refine learned memories stored as tokens instead of appending until overflow; updates can come from rich natural-language feedback instead of scalar rewards; the post does not claim this replaces weight updates — [Letta](https://www.letta.com/blog/continual-learning) [search]
- Skill learning: a reflection step feeds a learning agent that writes skills covering approaches, pitfalls and verification — [Letta](https://www.letta.com/blog/skill-learning/) [search]
- Context Constitution: a living document of context-management principles addressed to the agents themselves; a reviewer notes it is "prompt governance, not runtime code" — [Letta](https://www.letta.com/constitution/) [search]; [review](https://zby.github.io/commonplace/agent-memory-systems/reviews/context-constitution/) [search]

#### Lilian Weng (confirmed: the 2026 post exists)
- CONFIRMED. "Harness Engineering for Self-Improvement" was published on Lil'Log on 2026-07-04; it is a long research survey (harness design patterns, harness optimization, future challenges, benchmark appendix), not a how-to guide — [Lil'Log](https://lilianweng.github.io/posts/2026-07-04-harness/) [search]; [translation](https://github.com/deusyu/harness-engineering/blob/main/works/weng-harness-self-improvement-translation.md) [page]
- Three recurring design patterns: (1) workflow automation as a goal-directed plan / execute / observe-test / revise loop; (2) the filesystem as persistent memory (logs, diffs, error traces, rollout histories kept as files, exploiting models' skill with bash and file editing); (3) sub-agents and background jobs run by a small process manager, with outputs persisted to files so runs are inspectable and resumable — [translation](https://github.com/deusyu/harness-engineering/blob/main/works/weng-harness-self-improvement-translation.md) [page]
- Coding agents (Claude Code, Codex, OpenCode, Cursor-style) share one tool set: file search/edit, shell, git, MCP/skills, web, artifacts, cron, sub-agent delegation — [translation](https://github.com/deusyu/harness-engineering/blob/main/works/weng-harness-self-improvement-translation.md) [page]
- Optimization ladder: instruction prompts → structured context → workflows → harness code → optimizer code; near-term recursive self-improvement runs through the harness, not through models rewriting their weights — [translation](https://github.com/deusyu/harness-engineering/blob/main/works/weng-harness-self-improvement-translation.md) [page]
- Safety guidance for self-editing harnesses: evaluators and permission controls must sit outside the evolving harness, with held-out tests, trajectory audits and human review; the editable surface should be deliberately bounded — [translation](https://github.com/deusyu/harness-engineering/blob/main/works/weng-harness-self-improvement-translation.md) [page]
- Seven open problems: weak/fuzzy evaluators, context and memory lifecycle, negative results (keep failed attempts to prune search), diversity collapse, reward hacking, long-term success (sandbox rewards miss maintainability, migration cost, debugging burden), and the human role (move up the stack, do not remove) — [translation](https://github.com/deusyu/harness-engineering/blob/main/works/weng-harness-self-improvement-translation.md) [page]

#### François Zaninotto (Marmelab)
- Method: audit of 246 open-source repositories and 57 publications, limited to harnesses for coding agents — [Marmelab](https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html) [search]
- Recommendations (section headings): "Reduce The Harness To The Strict Minimum"; "Double Or Replace Rules With Scripts"; "Let The Agent Run The App"; "Measure How The Harness Is Actually Used"; "Don't Let the Harness Rot" / "A Harness Rots Quickly"; plus a "What Doesn't Work" section — [Marmelab](https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html) [search]
- Prose rules (CLAUDE.md, AGENTS.md) are called a weak point; prefer executable checks; test rules for both false positives and false negatives; instrument harness usage — [daily.dev mirror](https://daily.dev/posts/the-state-of-ai-harness-engineering-2026-z2cv9sfcz) [search]
- Research the report is said to cite: ETH Zurich result that machine-generated context files can lower success rates while raising inference cost; a Microsoft result that more than four agent-to-agent handoffs almost always fail; reviewer agents can degrade performance (all via a secondary README, not checked against originals) — [awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering/blob/main/README.md) [search]

#### Vivek Trivedy (LangChain)
- Definition: "Agent = Model + Harness"; the harness is every piece of code, configuration and execution logic that is not the model: system prompts, tools/skills/MCPs and their descriptions, bundled infrastructure (filesystem, sandbox, browser), orchestration, hooks/middleware — [LangChain](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness) [search]
- Filesystem is the most foundational primitive and also a shared ledger for multiple agents; bash is the general-purpose tool that lets the agent improvise, at the price of risk (hence sandboxes) — [summary of post](https://2ooks.github.io/knowledge-base/summaries/langchain-anatomy-of-agent-harness.html) [search]
- Context-rot defences: compaction near the limit; tool-output offloading (keep head and tail of large outputs, write the full output to a file); skills for progressive disclosure — [summary of post](https://businessdatasolutions.github.io/ai-wiki/sources/2026-03-10-trivedy-langchain-anatomy-of-an-agent-harness) [search]
- Long-running work: the "Ralph loop", where a hook intercepts the model's exit and re-injects the original prompt in a clean context window, with state carried by files, not by the prior conversation — [LangChain](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness) [search]
- Harness-tuning recipe from the Feb 2026 post: a plan / build (including tests) / verify against the spec / fix loop in the system prompt, middleware hooks around model and tool calls, and deliberate reasoning-budget allocation (more reasoning can cost over 2x tokens/time) — [LangChain](https://blog.langchain.com/improving-deep-agents-with-harness-engineering) [search]
- Detail I recall but did not re-confirm: named middlewares (pre-completion checklist, local-context mapping, loop detection for "doom loops") and a "reasoning sandwich" (highest reasoning for planning and final verification, lower in the middle) — [LangChain](https://blog.langchain.com/improving-deep-agents-with-harness-engineering) [bg, unconfirmed this session]

#### Nicholas Carlini (Anthropic)
- Harness: a bash `while true` loop restarts Claude Code with `AGENT_PROMPT.md` whenever a session ends; "Claude has no choice. The loop runs forever."; agents run in containers — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler) [page]
- Parallelism without an orchestrator: each of 16 agents has its own Docker container and clone of a shared bare repo; an agent claims a task by committing a lock file in `current_tasks/`; git sync makes a second claimant pick something else; merge conflicts are frequent and the agent resolves them; no inter-agent messaging besides git — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler) [page]
- Verification: "Write extremely high-quality tests"; the verifier must be nearly perfect because the agent will solve whatever the tests actually specify; a CI pipeline was added when new features kept breaking existing ones — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler) [page]
- Design for the agent: fresh containers have no context, so keep extensive READMEs and progress files; fight context pollution (print a few lines, log the rest to files, put "ERROR" and the reason on one grep-able line, precompute summaries); fight time blindness (sparse progress output, a `--fast` flag that runs a 1% or 10% deterministic-per-agent sample) — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler) [page]
- Make work parallelizable: independent failing tests parallelize; a monolithic task (the Linux kernel) did not ("Having 16 agents running didn't help because each was stuck solving the same task") until GCC was used as an oracle to compile most files so each agent chased different bugs — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler) [page]
- Specialized roles: one agent each for de-duplication, compiler performance, generated-code efficiency, Rust-idiom design critique and documentation — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler) [page]

#### Google (whitepapers, ADK, Gemini CLI, Jules)
- Whitepaper series: sessions hold a single conversation's history and working memory; memory is long-term persistence across sessions; the papers warn about "context rot"; Agent Quality sets logs, traces and metrics as the three pillars of observability and covers LLM-as-judge plus human evaluation; Introduction to Agents stresses Agent Ops, identity and policy constraints — [Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/a-devs-guide-to-production-ready-ai-agents) [search]; [summary](https://intellibytes.substack.com/p/context-engineering-explained-how) [search]
- ADK context model: context is "a compiled view over a richer stateful system", not a mutable string buffer; four layers (working context, session, memory, artifacts); artifacts are referenced by name and version instead of pasted into the prompt — [Google Developers Blog](https://developers.googleblog.com/en/architecting-efficient-context-aware-multi-agent-framework-for-production/) [search]
- Gemini CLI instruction files: hierarchical loading (global `~/.gemini/GEMINI.md`, workspace and parent directories, then just-in-time files discovered when a tool touches a path); `@file.md` imports to split large files; `/memory show` to inspect what the model actually receives and `/memory reload`; `context.fileName` can be set to a list such as `["AGENTS.md", "CONTEXT.md", "GEMINI.md"]` — [gemini-cli docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md) [page]
- Jules: reads `AGENTS.md` at the repository root (support added 2025); clones the repo into a cloud VM, plans, executes and opens a PR; supports an environment setup script — [Jules setup guide](https://thepromptshelf.dev/blog/google-jules-agents-md-setup-guide-2026) [search]

### Inferences
- Across OpenAI, Cursor, Anthropic, Letta, LangChain and Weng the common denominator is "state on disk, small context": plans, progress notes, handoffs, memory and logs live in files/git and are pulled in on demand. This is the least contested piece of advice in the set.
- "Instruction file as map" (Lopopolo), just-in-time context files (Gemini CLI), skills as progressive disclosure (Trivedy, Letta) and Zaninotto's "strict minimum" are the same idea at different layers: minimize always-loaded text.
- Every long-running system here relies on an outer restart mechanism instead of one endless context: Carlini's bash loop, Trivedy's Ralph loop, Cursor's fresh starts, Symphony's continuation turns, Codex compaction.

## Where do they contradict each other or earlier common advice?

### Takeaway
The sharpest disagreements are about gates and structure: whether to keep human or agent reviewers and merge gates (OpenAI adds review agents and reviews post-merge; Cursor deleted its judge and integrator; Carlini and Weng insist on strong external verifiers), whether locks and orchestrators are needed at all, and whether tool calls should be replaced by generated code. Several also overturn 2024-2025 defaults such as big instruction files, vector-store memory and mandatory pre-merge human review.

### Inferences
- The employer evidence favours: Lopopolo was at OpenAI through at least April 2026 and probably moved to Google Cloud in late August 2026. Everything he published about harness engineering describes OpenAI work. A report should attribute the work to OpenAI and note the reported move as unconfirmed by a primary source.
- The gate disagreement is largely explained by task type: where a strong external oracle exists (compiler test suites) a strict verifier is cheap and valuable; where the product is open-ended (a browser, an internal app) teams trade per-commit correctness for throughput and repair later. Neither camp has shown the other's setting fails on its own task.
- Model names in these sources (GPT-5.2, gpt-5.2-codex, Opus 4.5/4.6, Sonnet 4.5) are one or more generations old by November 2026. Model-specific advice (which model drifts, which stops early, reasoning budgets) should be treated as dated; structural advice (files, checks, isolation) has aged better.
- Weng's cited finding that mid-tier models gain most from harness work, and her prediction of internalization, suggest elaborate harness investment has a shrinking payoff on frontier models. This matches Zaninotto's "strict minimum" and Cursor's removals, and cuts against the heavier scaffolding in the OpenAI and LangChain write-ups.
